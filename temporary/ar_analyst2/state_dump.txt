# Capacity audit: depth/width coupling and the true param budget

## Correction: the model is ~50M params, not ~126M
`GPTConfig(vocab_size=32768)` is a default that is always overridden in `build_model_config(vocab_size=tokenizer.get_vocab_size())`. The shipped tokenizer has **8192** tokens (`prepare.py` `VOCAB_SIZE=8192`, incl. 4 specials). Correct decomposition at champion (DEPTH=8, ASPECT_RATIO=64 -> model_dim=512):

| component | params |
|---|---|
| transformer blocks (8 x 3.146M) | 25.17M |
| value embeddings (4 layers x 8192*512) | 16.78M |
| token embedding wte | 4.19M |
| lm_head | 4.19M |
| resid/x0 scalars | 16 |
| **total** | **50.33M** |

## The depth/width coupling
`model_dim = DEPTH * ASPECT_RATIO`, rounded up to a multiple of `HEAD_DIM`. So `DEPTH = 12` alone (AR still 64) gives model_dim=768 and 135.3M params (+169%) -- a depth+width+FLOPs compound change. To test depth alone, co-adjust AR:

| config | width | params | delta vs champion |
|---|---|---|---|
| DEPTH=6, AR=85 | 512 | 39.85M | -20.8% |
| DEPTH=8, AR=64 (champion) | 512 | 50.33M | 0 |
| DEPTH=12, AR=42 | 512 | 71.30M | +41.7% |

This is the bracket queued as `exp_cap_depth12_w512` / `exp_cap_depth6_w512`.

## Value embeddings dominate depth scaling
`has_ve(i, n_layer)` is parity-based (`i % 2 == (n_layer-1) % 2`). n_layer=8 -> VE on 4 layers; n_layer=12 -> VE on 6 layers; n_layer=6 -> VE on 3. Each VE is 8192*512 = 4.19M params, i.e. **more than the 3.15M transformer-block cost added by one layer**. Therefore:
- depth 8->12 adds 4 blocks (12.58M) + 2 VEs (8.39M) = +20.97M.
- A VE-count change is a first-class capacity dial: 8 VEs = +16.78M (+33%); 2 VEs = -8.39M (-17%).

## Baseline memory risk (flag for GPU agents)
At DEVICE_BATCH_SIZE=128, the final logits are [128, 2048, 8192]: 4.29GB bf16, 8.59GB after the explicit `.float()`; saved MLP intermediates are ~64*2048*2048*2 = 0.54GB (fc out) + 0.54GB (relu-square out) per layer, ~8.6GB over 8 layers at batch 64. At batch 128 activation memory roughly doubles to ~17GB, on top of ~8.6GB logits + ~2GB weights/optimizer -> ~28-30GB, right at the 32GB limit. **Recommended memory-safe baseline: DEVICE_BATCH_SIZE=64, TOTAL_BATCH_SIZE=2**19 (grad_accum=4) so optimizer-step semantics are unchanged.** Do not attribute a batch-64 baseline to the TOTAL_BATCH_SIZE axis; that is a micro-batch/memory change only.

## MFU reporting caveat
`H100_BF16_PEAK_FLOPS = 989.5e12` is hardcoded and used as the MFU denominator. On 2x RTX 4080S (~1/10 of that dense bf16 peak) `mfu_percent` is understated by roughly an order of magnitude. When applying the compute-budget audit rule, do not read the printed MFU as real utilization; use wall-clock step count and tokens/sec instead.
